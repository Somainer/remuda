# 首页：分诊优先（`/m` 与 `/sessions`）

> 状态：规格 v1，2026-10-30，docs-only。决策记录 [D-061](./decisions.md)。§0.2 列出的所有者裁定（2026-10-30）具有约束力。本文件是首页的机械权威：它与 [ui-spec.md](./ui-spec.md) 的旧描述冲突时，以本文件为准；ui-spec §2.1、§2.5、§3.1、§3.3、§4.5、§4.7、§6 已同步修订，只保留摘要并指回这里。令牌与控件以 [visual-system.md](./visual-system.md) 为准，Main 的机制以 [main-agent.md](./main-agent.md) 为准。

基线：origin/main `c27e0eac`。下文引用的代码位置都以这个提交为准。

## 0 原则

### 0.1 首页回答什么

首页只回答一个问题：**现在有什么需要我；其余的还好吗。**

- 页面上只有一个「需要你」队列，就是 §4 的队列。卡片能在首页一键处理，但首页授权的范围比收件箱和会话页小（§4.3）。
- Main 是队列上方的一张卡，加上底部一条「问 Main」输入条（§6）。它不是单独的 tab，也不占导航槽位。
- 队列下面是台账（会话列表）。台账和队列共用同一个 `rank()`，空闲的行折叠起来（§3）。
- 页头有一行计数（§5），下面是一条主机条（§1 ②）。数据是否新鲜按 §8 判定。

### 0.2 所有者裁定（2026-10-30）

1. **主轴 A，分诊优先。** `/m`（手机）和 `/sessions`（桌面）各有一个「需要你」队列，并且全页只有这一个。此外还有：一键作答、顶部的 Main 卡、底部的「问 Main」输入条、共享的 rank 与空闲折叠、计数行、主机条和新鲜度规则。PhoneNav 保持 4 个槽位。
2. **`ma-main-ui` 现在排期**（D-057；main-agent.md §15）。Main 卡与输入条紧随其后（§13）。
3. **完成未看（◉）按 owner 记，不按设备记。** ui-spec §3.1 与投影字段 `unseen` 已据此修改（§7）。
4. **glance 取 owner 范围**：Main 子树，并上 owner 自己开的会话（§5.3）。
5. **计数口径**：角标和「需要你」都等于两部分之和：真正在等 owner 的交互，加上没有对应交互、由 owner 阻塞的任务。Main 的提问只算一次。完成未看、通知和回合失败都不计入（§5）。
6. **首页可以用 chip 回答**同时满足以下条件的问题：单字段、单选、不是 sensitive、选项不超过 4 个（§4.2）。
7. **小界面授权更少。** 首页的权限卡只给「允许一次」和「拒绝」；计划卡只给「审阅计划」；永不批量批准。这条规则约束人类界面，不约束 Main（§4.3）。
8. **桌面列表里的裸按键 enter / esc / ctrl+c 移到终端页**，停止操作需要确认（§9 ⑦）。
9. **快捷提问 chip 只在输入条获得焦点时出现**（§6.3）。
10. **Hub 不内置早报模板。** 定时由 Main 自己用 `remuda wake add` 设置（D-060 决策 7）。
11. **不接入外部邮件或 IM 来源。** 外部事实只能以 Main 结论的形式出现，即「告诉你」卡。
12. **队列为空时显示一行问候**；h1 仍然是「会话」（§5.2）。

### 0.3 全局规则

- **一个 `rank()`。** 首页上所有列出会话的段，都用 §3 的同一个排序。
- **交互期间不重排**（§3.3）。
- **按钮一律单行**（visual-system §8.1）。
- **未知的数据显示「–」或者直接隐藏，绝不显示 0**（ui-spec §3.3）。
- **一个数据源失败，只影响它自己那一段。** 主机列表读失败不会让队列消失，交互列表读失败也不会让台账变空。
- **每个元素都写明数据来源**：要么是一条现有路由，要么是一个具名的计划任务（§1）。计划任务没落地的元素就不渲染，不画占位，也不用别的数据冒充。
- **不用绿色表示在线**（ui-spec §6）：绿色只用于权威确认。
- **数字只来自真实来源**，不加装饰性的未读点。

**不做的事：** 大号问候区、品牌图标、能力说明句、预设提问卡墙；单独的 Main tab 或 5 槽 PhoneNav；`/m/sessions`；手机上单独的「工作中」段（它和 rank 后的台账、收件箱的「进行中 · 最近」重复）；伪造的未读点；首页上的 allow-session、内联批准计划和批量批准；首页上的模式或权限选择器（只读的 model·effort chip 除外）；Hub 生成的早报模板；外部邮件和 IM。

### 2.4 断点

| 宽度 | 布局 |
|---|---|
| ≥1440 | 三栏：侧栏、主列、右栏 360（§2.2） |
| 1280–1439 | 右栏收起。③ Main 卡和 ⑨ 输入移到主列顶部，放在「需要你」上面。⑥「工作中」不单独成段，改为点击计数行的「工作中」后按状态筛选。⑩ 收成 Main 卡里的一行（§2.3） |
| 1024–1279 | 同 1280–1439。本设备没有显式的侧栏偏好时，`/sessions` 上的侧栏初始为 48px 图标列（与 ⌘B 收起后的状态相同）；⌘B 照常切换，切换结果按设备记住 |
| 768–1023 | 同 1024–1279 |
| compact（ui-spec §1.3 的查询） | 不渲染 `/sessions`，重定向到 `/m`（§2.1） |

布局只按宽度切换。命中区仍按 `pointer: coarse` 判定（ui-spec §3.4）。

### 2.5 首页上的 SpacesPanel 默认折叠

在 `/sessions` 上，SpacesPanel 默认**折叠**在主机条最右端的「空间 ▸」开关后面，不再常驻为索引列。展开之后：≥1024 时以索引列（宽 `--index`）出现在主列左侧；<1024 时以覆盖层出现。两种形态都沿用同一个组件和同样的 testid（ui-spec §1.4）。展开状态按设备存在 SpacePrefs（`web/src/features/spaces/store.ts`）里。

这条改变了现有行为（D-053 规定面板常驻、没有自己的折叠开关），所以在 D-061 里单独列为一条。`/m` 的「空间: 全部 ▾」页头按钮和 Space 抽屉不变。

## 3 排序与折叠：`rank()`

### 3.1 定义

`rank()` 只有一个定义，放在 `web/src/features/mobile/homeRows.ts`。`/m` 的台账、桌面的 `SessionList` 和 ⑥「工作中」都用它（任务 `home-rank-fold`）。

七个档位：

| 档 | 名称 | 点（ui-spec §2.1） |
|---|---|---|
| 1 | blocked | ⚠ |
| 2 | done-unseen | ◉ |
| 3 | working | ● |
| 4 | awaiting-wake | ○ 加状态词「待唤醒」 |
| 5 | starting | 脉冲点；lifecycle 未知或正在对账时画虚线环 |
| 6 | idle | ○ |
| 7 | exited | ■ |

**判定。** 档位从现有投影 `projectStatus`（`web/src/lib/status.ts`，ui-spec §2.1）推出，不另造状态机。输入有三个：
- `L` 是 Web 投影里的 `lifecycle`，取 `requested`、`preparing`、`starting`、`ready`、`running`、`closing`、`exited`、`failed`、`unknown`、`reconciling` 十个值之一。Hub 发来的其他字符串由 `mapLifecycle`（`web/src/lib/api.ts`）映射为 `unknown`。
- `A` 是 `activity` 的已知值，取 `idle`、`working`、`waiting-interaction`、`draining` 之一；activity 未知时记为「未知」。Hub 的 `blocked` 由 `mapActivity` 映射为 `waiting-interaction`。
- **活着** 指 `L ∈ {ready, running}`。一个刚跑完一回合、进程仍在的实例报告的是 `L=running`、`A=idle`，所以「空闲」一族（第 2、4、6 档）的判定对 `ready` 和 `running` 一视同仁，与 `projectStatus` 的 idle 分支相同。

判定按下表**自上而下，先命中先得**：

| 顺序 | 条件 | 档 |
|---|---|---|
| a | `A = waiting-interaction`（任何 `L`） | 1 blocked |
| b | `L ∈ {requested, preparing, starting, unknown, reconciling}` | 5 starting |
| c | `L ∈ {exited, failed, closing}` | 7 exited |
| d | `A ∈ {working, draining}` | 3 working |
| e | `A = idle`，`unseen=true`，并且没有 `lastTurnError`，即最近一个结束的根回合是成功的（§7）。失败的回合不进这一档，而是在队列里出一张回合失败卡（§4.5） | 2 done-unseen |
| f | `A = idle`，并且满足以下任一条：至少有一个子实例（子实例的 `parentInstanceId` 指向它）落在第 1、3 或 5 档；它所在血缘有一个未来的 wake（`home-wakes` 落地后） | 4 awaiting-wake |
| g | `A = idle` | 6 idle |
| h | 其余情形，也就是活着但 `A` 未知 | 3 working |

**这张表是全的。** 走完 b、c 两行之后，`L` 只剩活着的两个值，所以 e–g 隐含「活着」。`A` 的四个已知值和「未知」分别落在 a、d、e–g、h。因此每个 `(L, A)` 组合恰好得到一个档位。各个非活着的状态各对应一个档：`failed`、`closing`、`exited` → 7；`unknown`、`reconciling` → 5；`requested`、`preparing`、`starting` → 5。`draining` 属于 activity，对应第 3 档。

**和状态点的关系。** 档位只在两处偏离 `projectStatus`，其余与状态点逐条一致：
- **`connectivity` 不参与档位。** `connectivity ≠ connected` 只把点画成虚线环、把下一步写成「状态待确认」（ui-spec §2.1）；行仍按 `L` 与 `A` 排档。这样主机掉线时，blocked 的行不会掉出第 1 档。
- **`L ∈ {unknown, reconciling}` 时**，状态点是虚线环；档位走 a 行或 b 行。也就是说，已知在等人的行仍在第 1 档，其余的行与 starting 同排，不会被排到 idle 或 exited。

- **同一档内新的排在前面**：按 `lastEventAt` 降序，没有就用 `updatedAt`；时间相同时按 `instanceId` 排，保证结果确定。
- 第 2 档在 `seen-hub` 落地之前恒为空。第 4 档在 `home-wakes` 落地之前只按子实例判定。
- `homeRowsSignature`（`homeRows.ts`）必须把档位和下面的折叠字段都包含进去，否则档位变化时列表不会重画。

### 3.2 折叠与组头

- 每个项目组里，第 6 档（idle）的行折成「还有 N 个空闲 ▾」。第 7 档的行仍然进入现有的「已退出」/「已归档」折叠。
- 一个项目组里如果第 1–5 档都没有行，整组折进「安静的项目 · N ▸」。
- 搜索框有内容时，所有折叠强制展开（手机首页的搜索范围见 ui-spec §4.7）。
- 组头用点计数：`⚠1 ●2 ◉1 ○4`，单行，`white-space: nowrap`。计数为 0 的段不显示。
- 折叠状态按设备存在 SpacePrefs 里。

### 3.3 交互期间不重排

以下情况下，列表和队列都冻结当前顺序：指针或手指按在列表上、sheet 打开、hover 菜单或 ⋯ 菜单打开、焦点在某一行的控件上。在冻结期间到达的新数据照常更新行的**内容**（标题、点、下一步），但不移动行的**位置**。冻结结束后一次性重排。

## 4 「需要你」队列

### 4.1 组成与顺序

队列是全页唯一的「需要你」。从上到下依次是：

1. **Main 在问你**：Main 现行章节上的待处理交互，置顶，只计一次（`home-main-extras`）。
2. **其他待处理交互**：`GET /v1/interactions` 中 `status=pending` 且没有过期的项，派生规则和收件箱一样（`deriveInboxQueue`），顺序也和收件箱「待你处理」档一样。`routed-to` 落地后，`routedTo=main` 的项不进入队列（§5.1）。
3. **任务待你**：`GET /v1/tasks` 中未归档、`blockedReason` 非空、并且它的会话都没有待处理交互的任务（§4.6）。
4. **告诉你**：`home-to-you` 落地后，Main 用 `remuda owner notify` 发出、还没确认的通知（D-060 决策 7；`cb-owner-notify`）。
5. **回合失败**：`GET /v1/instances` 中带 `lastTurnError` 的实例（D-057 OA6），离开规则见 §4.5。

第 1–3 类计入「需要你」的数字（§5），第 4、5 类不计入。

**数量上限与展开：** 折叠时手机显示 3 张卡，桌面显示 4 张。
- **超出部分在首页原地展开，手机和桌面相同。** 超出的卡折成最后一行「还有 N 条 ▾」，N 是没有显示的卡数。点一下，整个队列就在首页原地展开，所有卡按 §4.1 的顺序列出；末行变成「收起 ▴」。展开状态不持久，重新进入页面时恢复折叠。
  - **为什么不跳页：** 队列里有收件箱显示不了的卡。收件箱只列交互，没有任务层（`InboxShell`），所以「任务待你」、「告诉你」和回合失败卡只能在首页展开里看到。
  - **展开期间**同样遵守 §3.3 的「交互期间不重排」。
- **「去收件箱 ›」是 header 右侧一个独立的链接，只管交互。**
  - 指向 `/m/inbox?focus=<最早一条交互>`，桌面指向 `/approvals?focus=`；
  - 队列里没有交互卡时，不渲染这个链接；
  - 收件箱目前只读 `focus`，回答之后不会自动跳到下一条，所以链接不叫「逐条处理」。

**搜索框有内容时，整个队列隐藏。**

### 4.2 卡片种类与首页上能做什么

首页卡片是 `ApprovalCard` 的一个新变体 `mode="home"`（任务 `home-queue`）。它沿用 ui-spec §2.5 的卡片外壳和按钮标签规则（按钮上直接显示 `opt.label` 的原文），只是能做的事更少：

| 卡片种类 | 判定 | 首页上能做什么 |
|---|---|---|
| 权限 | `request.kind=approval` | 只渲染 `effect` 为 `deny` 和 `allow-once` 的两个选项：「拒绝」「允许一次」。缺少其中任何一个时不渲染按钮，只给「去收件箱」 |
| 简单问题 | `request.kind=question`，同时满足：`fields.length=1`、`input=single-select`、`options.length ≤ 4`、`sensitive=false` | 每个选项一个 chip，另加「其他…」（打开会话页的表单）。推荐项如果有标注，原样显示 |
| 其他问题 | 不满足上一行条件的 `question` | 「去回答」（会话页表单） |
| 计划 | `request.kind=plan-review` | 标题、正文前 2 行，只有「审阅计划」（进会话页） |
| 终端提示 | native-tty 承载、没有结构化选项的提示 | 屏幕最后 3 行，「去终端」（`/s/:id/tty`） |
| sensitive / elicitation | 任一字段 `sensitive=true`，或 `request.kind=elicitation` | 只给「去会话」 |
| 任务待你 | §4.6 | `blockedReason` 一行，「打开任务」 |
| 告诉你 | `home-to-you` | 标题、正文前 2 行，「知道了」「打开对话」。「知道了」在所有设备上生效（owner 范围的确认） |
| 回合失败 | `lastTurnError` | 错误文本一行（原文，截断），「打开」「知道了」 |

D-061 修订了 ui-spec §2.5「AskUserQuestion 不在列表里填完」：上表「简单问题」一行是唯一的例外，而且只在首页成立。收件箱的行为不变。原生 tty 单字段问题在收件箱里的快答（`PtyQuestionAnswers`）也不变。

### 4.3 小界面授权更少

授权范围随界面变小而缩小：
- 首页只给「允许一次」和「拒绝」，**永远不给** allow-session；
- 计划永远不在首页批准；
- 没有任何界面提供批量批准（「全部允许」）。

更大的授权只能在收件箱或会话页给出。这是**人类界面**的规则，不约束 Main。Main 受它的 grant 和 D-017、D-051(a) 约束：approval 只由人回答，Agent 永远不回答 approval。

### 4.4 回答流程

- **不做乐观更新。** 点击后进入 answering 状态，按钮保持禁用，直到 `POST /v1/interactions/{id}/answer` 返回（现有行为，`web/src/lib/store.ts`）。
- **成功后**，卡片原地显示 2 s 回执「已提交」，然后离开队列。
- **409 或 410**（别的设备或别的回答先到了，或者交互已经离队）：卡片显示「已在其他设备处理」，然后离开队列。
- **其他错误**：错误文本显示在按钮下方，按钮恢复可点。
- **数据过期时**（§8）：按钮置灰，旁边提示「数据可能过期」。

### 4.5 失败卡如何离开队列

**`seen-hub` 落地之前，** 回合失败卡在以下任一情况下离开队列：
- 实例被恢复（产生新的实例）；
- 实例被关闭（`lifecycle` 进入 `exited` 或 `failed`）；
- 下一个回合开始。`lastTurnError` 会在下一回合开始时清掉，所以之后的回合成功了，卡自然就不在了。

另外，卡上有一个本设备的「知道了」，以 `(instanceId, lastTurnError.at)` 为键存在 localStorage。同一个实例再次失败时，键不同，卡会重新出现。

**`seen-hub` 落地之后，** 改为「被看过就离开」：只要 owner 的 seen 位置不早于失败回合的结束位置，卡就离开。这时「知道了」改为调用 `POST /v1/instances/{id}/seen`，所有设备上一起生效。

### 4.6 和任务层去重

- 首页只能有一个「需要你」，就是这个队列。台账（⑦）不再单独渲染任务层的「需要你」组（`buildHomeTaskLayer` 的 attention 组）。`/board` 和任务列表里的「需要你」组不受影响（ui-spec §2.9）。
- 一个未归档、由 owner 阻塞的任务（`blockedReason` 非空）：
  - 它的某个会话已经有待处理交互时，只显示那张交互卡，不显示任务卡；
  - 它的会话都没有待处理交互时，显示一张「任务待你」卡，操作是「打开任务」。
- 计数行和角标用同一套口径（§5）。

## 5 计数口径

### 5.1 「需要你」N 与应用角标

**N = A + B。** A 是真正在等 owner 的交互数：`status=pending`、没有过期，并且在 `routed-to` 落地后满足 `routedTo=owner`。B 是没有对应交互的 owner 阻塞任务数（§4.6）。

- **Main 的提问只算一次。** 它就是 A 里的一项，不会因为同时出现在 Main 卡上而再算一次。
- **不计入 N 的：** 完成未看、「告诉你」通知、回合失败。
- **应用图标角标 = N。** 页面打开时由 `syncAppBadge` 设置；PWA 关闭时由推送载荷的 `badge` 字段设置（ui-spec §4.5）。所以 Hub 的 `with_badge` 计数（`alerts.rs`）也必须用这个口径：`home-queue` 把 B 加进去，`routed-to` 把 A 收窄到 `routedTo=owner`。
- **导航上「收件箱」的数字**（PhoneNav、桌面侧栏）仍然是收件箱队列本身，也就是 A。所以 N 减去收件箱的数字，恰好等于「任务待你」卡的张数。D-061 因此修订了 ui-spec v0.2.4「OS 角标与收件箱队列同源」：OS 角标改为 N，收件箱导航计数不变。
- **`routed-to` 落地之前，** 按 D-051 转给 Main 的 worker 提问仍然出现在队列里，也计入 N，有重复计数的风险。§10 把这一点列为已知降级。

### 5.2 计数行

- **手机** `⚠N 需要你 · ◉N 完成未看 · ●N 工作中`。**桌面**在后面再加「今日完成 N」。
- **段的取舍：**
  - 没有真实来源的段直接隐藏：◉ 段在 `seen-hub` 前隐藏，「今日完成」在 `home-glance-d060` 前隐藏。
  - 首个快照到达之前，每段显示「–」。
  - 已知为 0 的段不显示。超过 99 写成「99+」。
- **队列为空（N=0）时，** 第一段换成一行问候：按本地时间显示「早上好」（05–12 点）、「下午好」（12–18 点）或「晚上好」（18–05 点），后接「· 都处理完了」，再接其余非零的段；如果其余各段也都是 0，就接「· N/M 主机在线」。h1 仍然是「会话」。
- **点击：**
  - 点「需要你」，滚动到队列；
  - 点「工作中」或「完成未看」，按该档筛选台账；
  - 再点一次，取消筛选。
- **数据过期时**（§8），整行变灰，并显示「更新于 HH:MM」。
- **数据来源：** 今天由 `GET /v1/instances`、`GET /v1/interactions` 和 `GET /v1/tasks` 推导。`home-glance-d060` 落地后改读 `GET /v1/owner/glance`。

### 5.3 owner glance

`GET /v1/owner/glance` 是 owner 范围的只读投影，范围是 Main 子树并上 owner 亲手开的会话。它由 `home-glance-d060` 提供，挂在 D-060 `cb-digest` 之后：D-060 的 `GET /v1/lineages/{id}/glance` 只覆盖一条血缘，这里需要的是 owner 范围。投影至少包含：
- §5.1 与 §5.2 的各段计数；
- 当日完成数；
- 每个会话一句确定性的 headline，取自 D-060 的 worker digest 字段，不由 Hub 调模型生成。

行数上限沿用 lineage glance（等待与工作中各 50 行）。它落地后，首页删除对每一行逐个读 journal 的 2.5 s 轮询（`HomeList.tsx`），每个轮询周期只读一次 glance。

## 6 Main 卡与「问 Main」

### 6.1 解析

首页上的 Main 解析和 ui-spec §2.1 原「Main 置顶行」相同，并且必须和 `ma-main-ui` 共用同一处解析代码。规则是：
- 取持有 `address-owner` 的血缘的现行章节；
- 血缘暂停时，取最近一条 address-owner 血缘的最新章节；
- 没有 address-owner 血缘时，③ 和 ⑨ 都不渲染。

在首页上，Main 是一张卡加一条输入条，不是单独的 tab 或导航槽，也不再是列表里的置顶行（main-agent.md §9）。

### 6.2 Main 卡（③）

- **第 1 行：** 状态点、「Main」、一个状态短语，例如：
  - 「工作中 · 在看 SE-12 的 gate · 3分」
  - 「在问你」
  - 「空闲 · 21:04」
  - 「已暂停」
  - 「主机 forge 离线 · 2h」（琥珀色）
- **第 2 行：** Main 最近一条回复的首行。刚发送之后换成「已发送 · Main 正在处理…」。消息被拒时这一行变红，并给「重试」。
- **可选第 3 行（⑩）：** 「◷ 下次 09:00 <名字> · 共 N 个 ›」，只在有 wake 时出现。点开是一个 sheet，可以逐条取消（`DELETE /v1/lineages/{id}/wakes/{wakeId}`）。下次触发时间可能为 null，这时显示「—」，绝不显示 00:00 或纪元时间。
- **桌面右栏另外显示：**
  - 只读的 model·effort chip 和章节号；
  - 「展开 ›」：打开 `/s/:mainId`。
- **点卡片本身：** 打开 `/s/:mainId`（ui-spec §2.2 的「Main 会话」）。

### 6.3 「问 Main」输入条（⑨）

- **控件：** 复用 compact `Composer`，单行高度 **56px**（ui-spec §2.2 的 compact composer 边界，D-042），不另起数值。桌面用内联输入框，⌘↵ 发送。
- **发送：** 走 `POST /v1/instances/{mainId}/commands`，带 commandId（D-055 的 outbox）。
- **结果未知时：** 用 `GET /v1/instances/{id}/commands/{commandId}` 对账，绝不自动重发。
- **章节已被取代：** 消息发给了已被取代的章节、被拒收时，按钮变成「发送给当前 Main」，并且生成一个**新的** commandId（main-agent.md §9）。
- **血缘暂停：** 发送键变成「恢复」。
- **Main 的主机离线：** placeholder 提示「消息会排队，主机上线后送达」。
- **语音：** 只在 `SpeechRecognition` 或 `getUserMedia` 可用时渲染语音按钮（ui-spec §4.8）。iOS 独立 PWA 上不可用，就不渲染，不放一个点了没反应的按钮。
- **快捷提问 chip**（`home-main-extras`）：
  - 只在输入条获得焦点时出现。候选是：谁在等我、昨晚跑完了什么、哪些卡住了、今天落地了什么。
  - 只有存在真实计数时，chip 才带数字（例如「谁在等我 2」）。
  - 只列出 Main 当前 grant 能回答的问题。
  - 点 chip 只把文字填进输入框，发送仍然要另点一次。

### 6.4 交给 Main（`home-main-extras`）

「交给 Main」只出现在问题卡和计划卡的 ⋯ 菜单里，**审批卡上永远没有这一项**：
- 交互内容以不可信引用的形式发给 Main；
- 交互本身保持 pending，直到真正被回答。

## 7 完成未看与 seen（按 owner）

- **作用域：** seen 按 owner 记，不按设备记，所以手机和桌面看到的结果一致。推送订阅仍然按设备记（ui-spec §3.1）。
- **存储（`seen-hub`）：** 新表 `instance_views(instance_id, scope, seen_seq, seen_at)`。`scope` 目前只有 owner 一个取值。`seen_seq` 只增不减。
- **写入：** `POST /v1/instances/{id}/seen {durableSeq}`，幂等，结果是 `seen_seq = max(seen_seq, durableSeq)`。只接受 Human 设备的凭据：seen 是 owner 的注意力状态，Agent 不能替 owner 写。
- **投影：** `GET /v1/instances` 的每一行增加 `unseen: boolean`。当实例最近一个结束的根回合，其结束位置晚于 `seen_seq` 时，`unseen` 为真。这个回合成功时，行进入 §3 的第 2 档 ◉；失败时，行在队列里作为回合失败卡（§4.5）。
- **什么时候标为已看：**
  - 在页面可见时打开 `/s/:id` 的任一视图；
  - `/s/:id` 正在显示时回合结束；
  - 行菜单里的「标为已看」；
  - ⑤ 的「全部看过」，对列出的每一行各写一次。
- **本地与其他设备：** 本设备乐观更新。其他设备在下一个轮询周期（`GET /v1/instances`）里看到 ◉ 消失。
- **恢复与章节：** 恢复出来的实例、以及 Main 的后继章节都是新的实例 id，没有 seen 行；它们要等自己的回合结束之后才可能出现 ◉。首页只对 Main 的现行章节显示 ◉。
- **⑤ 刚完成：**
  - 手机最多 3 行，桌面最多 3 个行内项，超出写成「+N」；
  - 行标题加粗，用 ◉ 标记；
  - 操作是「打开」（同时标为已看）、「标为已看」、「全部看过」；
  - 没有 ◉ 的行时，整段隐藏。

## 8 新鲜度

**常量**（产品常数，写在这里；受 gate 约束的测试用注入时钟断言它们，不用墙钟毫秒阈值）：

| 常量 | 值 | 依据 |
|---|---|---|
| 轮询周期 | 2 s | `web/src/lib/store.ts` 的 `startPoll` |
| 过期阈值 | 10 s 内没有成功的 refresh（约 5 个轮询周期） | 本节 |
| 横幅去抖 | 连续失败满 5 s | 本节 |
| 回执 | 2 s | §4.4 |

**判定**（任务 `home-freshness`：从 store 暴露「最近一次成功 refresh 的时间」，并提供 `useHomeFreshness()`）：

- **新鲜：** hubStore 的连接状态是 live，**并且**最近一次成功 refresh 距今不超过 10 s。
- **过期：** 不新鲜，并且不处在下面的前台宽限期内。
- **前台宽限期：** 从页面回到前台（`visibilitychange` 变为可见），到之后的第一次 refresh 结束（无论成败）为止，**不判过期**。在这段时间里卡片按钮保持可点，并发冲突由现有的 409/410 路径兜底。如果不这样做，每次切回 App 按钮都会先被禁用一下。回到前台时做一次完整 refresh 是现有行为（`web/src/app/PhoneShell.tsx`）。
- **过期时：**
  - ④ 的按钮置灰，并提示「数据可能过期」；
  - ① 变灰，并显示「更新于 T」；
  - ⑦ 缓存的行变灰；
  - 其余段保持原样。
- **横幅：** refresh 连续失败满 5 s 才出现，高 32px，文案是「连不上 Hub · 上次更新 N 秒前 · 重试」。任何一次成功的 refresh 都会清零计时并收起横幅。连续失败 4 s 之后恢复，横幅不会出现。
- **首个快照之前：**
  - ④ 显示 2 张骨架卡，⑦ 显示 3 行骨架，① 显示「–」；
  - **绝不显示空态。** 冷启动时不能闪出「暂无会话」。
  - 空态和搜索无结果分开设计：「还没有会话」配「新建会话」，「没有匹配的会话」配「清除搜索」。

## 12 真实条件检查（RC）

每个面向用户的首页切片在 DONE 之前都要做一次真实条件检查。

- **配置：**
  - 复用 `web/playwright.mrealdevice.config.ts` 或 `web/playwright.webkit-hub.config.ts` 里的 WebKit iPhone project，以及 `m-realdevice.hub.spec.ts` 的软键盘写法（聚焦输入后缩小 visualViewport）；

- **视口：** 390、1280、1440，浅色和深色都要跑。
- **后端：**
  - 用 worker 自己构建、跑在自己端口上的 Hub 和 Node，不用 `remuda dev`，也不用 herdr；
  - 至少有一个**真实的** claude-sdk worker，跑在 owner 默认的 `auto` 模式下。
- **断网：** 用 `context.setOffline(true)`。离线场景只停自己 pid 文件里的 Node。
- **测试纪律：** 新的 hub spec 在缺少触发变量时自动 skip；受 gate 约束的测试里不用毫秒阈值。

### 12.1 队列任务用的授权动作

`home-queue` 的 RC 需要一个真实 worker 在 `auto` 模式下稳定地弹出一次权限请求。`auto` 模式没有例行弹窗，由一个审查模型先筛动作（[permission-modes-1](./evidence/permission-modes-1.md)），所以动作必须是审查模型会交给人决定的那一类。

- **候选动作（按顺序试）：**
  1. 让 worker 用 Write 工具在一个**私有的临时 git 仓库**里新建 `.git/remuda-rc-probe`。这个仓库由 RC 在自己的 scratch 目录里 `git init`，并注册成该 worker 的 workspace。`.git/` 下的写入属于 harness 不会自动批准的路径。
  2. 让 worker 用 Bash 删除 RC 事先建好、位于 worker 工作目录**之外**的一个临时目录（`rm -rf <scratch>/rc-victim`）。
- **先探测：** 正式跑 RC 之前，先用一次真实会话确认所选动作确实弹出了授权，也就是 journal 里有一条 approval 交互。把 Claude Code 版本和这条交互的种类记进证据。
- **两个都不弹时：** 把**这一个** RC worker 改成 `manual` 模式，用 Bash 执行 `touch rc-probe`。在 brief 回复里写明理由和版本。
- **禁止：** 在 Remuda 自己的 checkout、任何共享仓库，或者任何别人的 `.git` 里执行这些动作。
- **交互路由：** RC 环境里要么没有 address-owner 血缘，要么 D-051 开关是关的（它是 Hub 进程环境变量，D-051）。否则 worker 的提问会转给 Main，不进入「需要你」。
- **同一个 RC 的问题部分：** 让真实 claude worker 发一个 3 个选项的 AskUserQuestion。`auto` 模式下它走 `PreToolUse`（[askq-pretooluse-1](./evidence/askq-pretooluse-1.md)）。在 WebKit iPhone 上从 `/m` 回答之后，读 `GET /v1/instances/{id}/journal`，断言 worker 确实继续往下执行了。
