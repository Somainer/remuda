# Security review 2 — Hub auth, Hub↔Node transports, SecretBroker, generic-pty, MCP, Feishu, Web

Date: 2026-09-13
Scope: everything merged since `docs/design/security-review-1.md` (`19237a9`), i.e. `19237a9..425b20c` — 197 commits, ~63k lines. Areas: Hub auth (device tokens, bootstrap, pairing), Hub↔Node hello/auth over WSS and stdio, `SecretBroker` + provider profiles, `generic-pty` and the herdr socket, `tty.write`/keys and the raw tty input channel, worktree creation and the MCP tool surface, the Feishu dispatcher, and the Web client (cookie/bearer, WS auth, CSP).
Method: adversarial read plus live proof-of-concept against a locally bound Hub for W1. Line numbers refer to the tree at `425b20c`. `docs/design/remote-terminal.md` is not on this branch (it is on `origin/wt/x-term/tty-stream`, `e59605b`), so the raw tty input channel is reviewed from the code paths it will use — `tty.write`/keys plumbing, the follow WS, and the binary frame handler — rather than from the contract; the items tagged for x-term/x-termui below are the ones to re-check against that doc before it lands.

Severity:

- **P0** — exploitable with the current API without extra bugs; integrity or authz break.
- **P1** — realistic exploit path or secret-handling defect; should not ship as-is.
- **P2** — defense-in-depth, single-user residual, or config footgun.

A note on the threat model, because it decides most of the severities below. Three of the P0s (M1, M2, M3) are only "bugs" if you accept that **an agent instance is an untrusted principal**. An agent's context contains repo content, web pages, tool output, and bot text, any of which can carry an injected instruction. Today the MCP surface treats every tool call as if the operator typed it. If the project's actual position is "the agent is trusted, the operator accepts model-driven fleet control," then M1–M3 are by-design and should be *written down* as such — but D-011 (bot must never bypass human approval, `security-review-1.md:61`) says the opposite, and the `LaunchOrigin` enum exists precisely to encode that distinction. I have reviewed against D-011. That conflict is itself the finding (M0).

Review-1 follow-ups verified fixed on this tree: H1 (`store.rs:655-658` rejects cross-host `ensure_instance`), H2 (`config.rs:124-135` `secret_eq`), H3 (`auth.rs:50-63` `mode(0o600)` + `sync_all`), H4 (`auth.rs:114` `SameSite=Strict`), S1 (`remuda-ssh/src/target.rs:183-196` `validate_alias`), F1/F2/F3 (Feishu `admit()` chain intact, `inbound.rs:481-522`). H5 (immortal bootstrap) is unchanged and is now worse — see A2.

## P0

### W1. Unauthenticated path traversal in the Hub static handler → arbitrary file read → full Hub takeover

- **Where:** `crates/remuda-hub/src/web.rs:14-30`. `let raw = uri.path().trim_start_matches('/')` then `root.join(path)` with no normalization, no `..` rejection, no containment check. Reached via `lib.rs:194` `.fallback(static_fallback)` — the fallback is **outside** every `require_device` / `require_origin` gate.
- **Evidence (live PoC, not inferred).** I ran the Hub's own example (`crates/remuda-hub/examples/serve.rs`) with `REMUDA_WEB_ROOT=/tmp/travroot`, `REMUDA_DATA_DIR=/tmp/travdata`, bound to `127.0.0.1:55571`, and sent raw requests with `nc` (curl normalizes `..` client-side; axum/hyper do **not** normalize server-side — separately confirmed: a bare axum fallback receives `PATH=/../../../../etc/passwd` verbatim):

  ```
  GET /../../../../../../etc/hostname  → <the host's real hostname>   (byte-for-byte match)
  GET /../../etc/passwd                → <the node user's passwd line>
  GET /../travdata/bootstrap-token     → <the Hub's real bootstrap token, byte-for-byte>
  ```

  The traversal read the Hub's own `bootstrap-token` despite that file being mode `0600` — file permissions are irrelevant because the Hub process reads it as itself.
- **Exploit:** Any unauthenticated client that can reach the Hub port `GET /../<path>`s the bootstrap token, then `POST /v1/login` with it (`http.rs:146`) to mint a device token and cookie. That is full control of the Hub: list/create instances, answer interactions, create worktrees, drive every connected Node. Same primitive also reads `hub.sqlite` (Argon2 hashes, journals), `vapid.json`, `~/.ssh/id_*`, `~/.aws/credentials`, and any provider-profile secret file.
- **Scope caveat, stated honestly:** this only fires when `web_root` is set (`config.rs:30`), i.e. `remuda hub --web-root …`, `remuda dev --web-root …` (`cmd/dev.rs:74-76`), or `REMUDA_WEB_ROOT`. The default is `None` (`config.rs:69`), where serving is `rust-embed` `WebAssets::get(path)` (`web.rs:32`) and a `..` key simply misses the embedded map — not vulnerable. So: **not every deployment, but every `--web-root` deployment, and that is the documented dev/dogfood path.** Combined with the default listen of `127.0.0.1` (`config.rs:65`) the unauthenticated reach is usually local — but "local" includes any other process, container, or user on the box, and the deploy runbook puts a Caddy reverse proxy in front (`deploy-runbook.md:133-141`), which would forward the raw path upstream.
- **Fix:** Reject any request path containing a `..` segment, a NUL, or a leading `/` after trim, **before** joining. Then canonicalize the joined path and verify it is still inside the canonicalized `web_root` (`Path::starts_with` on canonical forms, which also closes symlinks inside the root). Serve only regular files. Add a regression test that raw-sends `GET /../../etc/passwd` and asserts a 404 — a `reqwest`/`curl`-based test will silently pass because the client normalizes, so the test must write the request bytes to a socket directly.

### M0. `origin` is decorative end to end: the Human/Bot distinction never reaches the gate that consumes it

- **Where:** the client stamps it — `crates/remuda/src/cmd/instance.rs:426` `"origin": origin` (MCP passes `"mcp"` at `cmd/mcp.rs:284`, CLI `"cli"`, fleet `"fleet"`). Nothing ever reads it back: `rg 'get\("origin"\)' crates/remuda-node crates/remuda-hub` returns **nothing**. The Node then hardcodes the value the driver will see: `crates/remuda-node/src/runtime.rs:897` `origin: CommandOrigin::Ui` and `crates/remuda-node/src/native.rs:345` `origin: InputOrigin::Human`.
- **Why this is the structural finding:** `materializer.rs:526-538` is review-1's D1 fix and it is correct in isolation — it refuses `DontAsk`/`BypassPermissions` when `origin == LaunchOrigin::Bot`. But `LaunchOrigin` is only ever reached through `From<CommandOrigin>` (`materializer.rs:126-134`), which maps `Ui | Cli | Mcp | System → Human`. So (a) the wire origin is dropped before it gets there, and (b) even if it survived, **`CommandOrigin::Mcp` is classified as `Human`**. The one gate that exists cannot fire for an agent-driven launch.
- **Exploit:** Every finding below that says "with the operator's authority" rests on this. An injected agent's MCP call is indistinguishable from an operator keystroke at every sink in the system. Concretely: `permission_mode` **is** wire-controlled — `native.rs:374-380` parses `"bypassPermissions"` and `"dontAsk"` straight out of `CreateInstanceRequest.permission_mode` (`remuda-node/src/model.rs:76`) — while origin on the same request is hardcoded `Human`. So the one input that selects bypass is attacker-reachable and the one input that would refuse it is not. (The MCP tool schema does not currently expose `permissionMode`, `cmd/mcp.rs:390-413`, so this is reached via the Hub/Node API rather than an MCP arg — but nothing enforces that gap.)
- **Fix:** Two changes, both needed. (1) Plumb the wire `origin` through Hub → Node → driver instead of hardcoding `Ui`/`Human` at `runtime.rs:897` and `native.rs:345`. (2) Map `CommandOrigin::Mcp` to `LaunchOrigin::Bot` (or add a distinct `Agent` variant and treat it as untrusted), so D-011 actually binds. Make `LaunchOrigin::Human` non-`Default` (`materializer.rs:111-112`) so a missing origin fails closed rather than silently becoming Human.

### M1. MCP tools are a confused deputy: any instance id, no ownership check, no approval

- **Where:** `crates/remuda/src/cmd/mcp.rs:270` `call_tool` — no authorization branch anywhere in the dispatch. `mcp.rs:274-286` `remuda_instance_send` takes `instanceId` raw; `mcp.rs:326-347` `remuda_instance_stop` / `remuda_instance_rm` likewise.
- **Exploit:** The `remuda mcp` process holds the operator's Hub device token. A prompt-injected agent calls `remuda_instance_send`/`_stop`/`_rm` against **any** instance id — a sibling worker, the coordinator's own instance — or `remuda_instance_create` on any host. Injection in one agent's context becomes fleet-wide control.
- **Fix:** Scope agent-origin calls to the caller's own `instanceId` (the MCP server knows which instance it was launched for). Cross-instance `send`/`stop`/`rm`/`create` require either a human-approval step or an explicit operator-granted capability. Gate in `call_tool`, not by stamping a string into the payload.

### M2. `remuda_fleet_send {all:true}` broadcasts attacker text to every instance on every host

- **Where:** `crates/remuda/src/cmd/mcp.rs:362-373` reads `all` straight from agent args; `crates/remuda/src/cmd/fleet.rs:195-215` sets `allowed_hosts = None` when `all` is set and the loop at `fleet.rs:217-250` sends to every instance from `list_instances()` with no filter and no approval.
- **Exploit:** One injected agent calls `remuda_fleet_send {all:true, text:"<injected instructions>"}`. The payload is delivered as a new turn to every running agent across the fleet — injection with a propagation primitive, which is the difference between one compromised worker and all of them.
- **Fix:** Forbid `all:true` from agent origin outright; require human approval for any fleet-wide send.

### M3. `generic-pty` + `remuda_instance_keys` is arbitrary command execution, and generic-pty force-enables yolo flags

- **Where:** `mcp.rs:401-404` lets the agent choose `driver` (`"pty"` → `generic-pty`); `mcp.rs:322-325` → `instance.rs:808-863` `encode_one` accepts any single character plus `enter`/`ctrl+c`, i.e. an arbitrary byte stream into a PTY.
- **Compounding, and worth flagging on its own:** `generic_pty.rs:1227-1233` `merge_yolo_argv` appends the preset's bypass flag **unconditionally** — every preset hardcodes one (`generic_pty.rs:70` `--dangerously-skip-permissions`, `:79` `--dangerously-bypass-approvals-and-sandbox`, `:88` `--always-approve`, `:97`, `:106` `--yolo`). It runs at `generic_pty.rs:337`, *after* `materialize()` at `:336` — so it is downstream of the D1 origin gate in `permission_plan` and no origin check applies to it (`rg origin generic_pty.rs` → only `:162`, `:194`, `:334`, all plumbing). A generic-pty instance is a sanctioned no-approval agent by construction.
- **Exploit:** Agent creates a `generic-pty` instance, then types a shell command followed by `enter` via `remuda_instance_keys` — code execution as the Node user, no approval prompt anywhere in the path.
- **Fix:** Treat pty attach/keys as privileged: human approval for tty writes from agent origin, and scope keys to the caller's own instance. Gate `merge_yolo_argv` on `LaunchOrigin` (after M0), or drop the hardcoded yolo argv and require it to be requested explicitly through `permission_mode` so the existing gate sees it.

### A1. Bootstrap token can claim an existing `host_id` → Node impersonation

- **Where:** `crates/remuda-hub/src/store.rs:432-445`. After the per-host Argon2 loop misses, a presented secret equal to the bootstrap is accepted; then `if load_host(conn, &host_id)?.is_some()` **returns `Authenticated` for that existing host** instead of rejecting the collision. `host_id` is fully client-supplied via hello (`ws.rs:237-245`).
- **Exploit:** Anyone with the bootstrap token (standing secret, see A2; readable outright via W1; distributed to every node by env, `remuda-node/src/enroll.rs:50-53`, `carrier.rs:66-71`) connects to `/v1/node` and sends `runtime.hello {hostId: "hst_<victim>"}`. The Hub authenticates them **as that host**. Note the asymmetry that makes this a bug rather than a policy choice: the per-host-token branch immediately above (`store.rs:422-431`) correctly authenticates a node as *its own* host and **ignores** the claimed `hostId` — only the bootstrap branch honors it. The attacker's transport is then registered at `ws.rs:295-301`, bumping the generation and **stealing the routing slot from the real Node**, so Hub→Node commands for the victim host (`instance.*`, `tty.write`) are delivered to the attacker. They can also serve forged `worktree.list`/`interaction.list` results and append journal entries under the victim's instances — all of which now pass the H1 host-binding check, because they *are* the host as far as the Hub is concerned. This re-opens H1 through the enrollment path rather than the journal path.
- **Fix:** Bootstrap should only ever mint a **new** host. If the requested `host_id` already exists, reject unless the presented secret verifies against that host's own `token_hash`. (The existing-host branch appears to be intended for re-enroll idempotency; that case should require the host token, not the bootstrap.)

## P1

### A2. Bootstrap token is a standing, unlimited, unrotatable join secret

- **Where:** `store.rs:432-462`; `auth.rs:68-84` `resolve_bootstrap` reads it back from disk on every start, so it is stable across restarts. Review-1 raised this as H5 and left it to owners.
- **Why it is now P1, not a policy note:** it is the pivot for both W1 (read it, become an admin device) and A1 (present it, become an existing host). A single long-lived secret that grants both device login and host identity, with no expiry, no use count, and no rotation path, is the highest-leverage thing in the system.
- **Fix:** Decide the policy and implement it: one-shot or count-limited enroll tokens, TTL, and a rotate command. At minimum separate the **device-login** secret from the **node-enroll** secret so one leak does not grant both.

### M4. Worktree `path` / `repo` are unvalidated — escape the intended worktree location

- **Where:** `mcp.rs:348-353` passes agent-supplied `path`/`repo` through; `crates/remuda/src/cmd/worktree.rs:196-206` `resolve_path` returns the caller's path as-is when absolute, else `repo.join(raw)` — no traversal or containment check. Only `name` is validated (`worktree.rs:163-173`, `[a-z][a-z0-9_-]{0,31}` — that part is solid). Identical logic Node-side at `crates/remuda-node/src/worktree.rs:67-75` and `:191-201`, reachable from Hub RPC `worktree.create`, which `http.rs:366-371` forwards `path`/`repo` into verbatim from `POST /v1/worktrees`.
- **Exploit:** `remuda_worktree_create {name:"x", path:"/home/op/.config/systemd/user"}` or `path:"../../../../tmp/evil"`. `git worktree add` (`worktree.rs:111-121`) creates the directory and writes a full checkout of `base` there — attacker-chosen directory creation and file placement as the operator/Node user, plus the ability to operate on a different repo via `repo`.
- **Fix:** Canonicalize the resolved path and require containment under a fixed base (`<repo>/../remuda-wt/`); reject absolute paths and `..` components; do not expose `path`/`repo` on the MCP tool at all.

### M5. `file` / `promptFile` give an agent arbitrary local file read

- **Where:** `mcp.rs:378-388` `send_text_from_args` — `std::fs::read_to_string(path)` on an agent-supplied path, used by `remuda_instance_send` (`:277`) and `remuda_fleet_send` (`:363`); `mcp.rs:392-396` same for `promptFile`. Both are advertised in the tool schema (`mcp.rs:141`, `:224-225`, `:255`), so the model is actively invited to supply them.
- **Exploit:** `remuda_instance_send {instanceId:<own>, file:"~/.ssh/id_ed25519"}` — or the Hub's `bootstrap-token`. Contents become the prompt and come back out through the journal via `remuda_instance_read`. This defeats the `remuda-mcp.md:58` mitigation ("do not put the bootstrap token in the prompt"), since the token file itself is readable.
- **Fix:** Drop `file`/`promptFile` from agent-callable tools, or confine reads to an explicit allowlisted directory.

### T1. Node stdio transport dispatches instance methods with no authentication

- **Where:** `crates/remuda-node/src/stdio.rs:272-284` answers hello unconditionally; `:286-301` dispatches interaction and `instance.*` methods with no token check anywhere in the inbound path (the token at `:141-151` is what the Node *sends outbound* to the Hub, not something it verifies on input).
- **Assessment:** the trust assumption is that stdin comes from `ssh <alias> -- <remote_bin> node --stdio` (`remuda-ssh/src/transport.rs:77`, `:304`), so authentication is SSH's job. That is defensible, and I am not calling it a break. It is P1 because it is **undocumented and unenforced**: anything that can write to that Node's stdin — a wrapper script, a misconfigured supervisor, a local process that inherits the fd — gets unauthenticated `instance.create`/`send`/`interaction.respond` on that host.
- **Fix:** Document the trust boundary in `stdio.rs`. Optionally require `node.auth` before non-hello methods on stdio too, mirroring the WSS path (`ws.rs:165-172`), so the carrier is not the only thing standing between stdin and instance control.

### G1. All instances share one unauthenticated herdr session — a PTY instance can read and drive every sibling

- **Where:** every instance on a node is pointed at the **same** session: `crates/remuda-node/src/native.rs:68` `herdr_session: "remuda-node"`, `herdr_socket_dir: None` (`native.rs:64`), applied at `native.rs:216-218`. That resolves to one socket, `~/.config/herdr/sessions/remuda-node/herdr.sock` (`remuda-herdr/src/client.rs:491-497`). The parent dir is created with `create_dir_all` and no explicit mode (`server.rs:64-66`), and the RPC does no credential exchange at all — `rpc.rs:113-121` is a bare `UnixStream::connect` + write. Verified on this host: the sockets themselves are `srw-------` and dirs `drwxrwxr-x`, so **other users are excluded**. The PTY child, however, runs as the *same uid*.
- **Exploit:** The herdr API is unauthenticated by design — "can connect" is "can control" — and the shared session means that control is not scoped to the caller's own instance. Exposed on that one socket: `pane_read`/`agent_read` (`client.rs:189`, `:289`) to read **every sibling instance's screen**, `pane_send_text`/`pane_send_keys`/`agent_prompt` (`:195`, `:212`, `:257`) to **type into a sibling agent**, `workspace_create`/`pane_split`/`agent_start` (`:128`, `:171`, `:242`) to spawn unbounded new shells, `session_snapshot` (`:329`), and `server.stop` to kill the node's whole session. M3 gives a generic-pty instance a shell, and `server.rs:78` `env_remove("HERDR_SOCKET_PATH")` prevents *inheriting* the path but not *deriving* it — it is a fixed constant. This is a full escape from the instance into every other instance on the host.
- **Fix:** Per-instance `session_name`/`socket_dir` so panes are not co-resident, and/or an auth token on herdr RPC with `SO_PEERCRED` verification on accept. Create the session dir `0700` explicitly rather than relying on the ambient umask. If the shared session is deliberate, it must be documented — and then M3's "an agent may choose `driver:pty`" has to close, because that is the opt-in to this tier.

### G4. The PTY child inherits the Node's full environment, including provider secrets

- **Where:** the herdr daemon is spawned inheriting the Node's env, removing only three HERDR variables (`remuda-herdr/src/server.rs:69-78`) — `ANTHROPIC_*`, `REMUDA_*`, and any provider token are **not** removed, and every pane it forks inherits them. The driver's own pane env is minimal and does **not** apply the recipe's `env_allowlist`, which is computed only for the audit record (`materializer.rs:349-404` vs `generic_pty.rs:357-367`).
- **Exploit:** The agent runs `env` or reads `/proc/self/environ` and harvests whatever the Node process holds. None of the per-instance secret scoping that the Claude token-broker provides (`materializer.rs:917-968`, the `apiKeyHelper` pattern that correctly keeps the key out of argv and env) applies to generic-pty. `CLAUDE_CONFIG_DIR` is pinned only when `native_home/.claude.json` already exists (`generic_pty.rs:361-364`); otherwise the agent falls back to the node user's default Claude credentials and MCP servers.
- **Fix:** Spawn the daemon and the pane with a scrubbed env — pass only the materialized `env_allowlist` and strip provider tokens. Extend the token-broker pattern to generic-pty instead of leaking process env.

### G5. `cwd` from the create request is not constrained to the workspace

- **Where:** `crates/remuda-node/src/runtime.rs:194-199` takes `request.cwd` as `workspace_root` whenever it `is_dir()`, with no containment check against the registered workspace or worktree. It reaches the pane verbatim at `generic_pty.rs:374` and `:384`. The only validation anywhere is "must be absolute" (`materializer.rs:465-470`) — no `..` rejection, no symlink resolution, no root-prefix enforcement.
- **Exploit:** A create request with `cwd:"/"` or `cwd:"/home/<user>"` starts the (always-yolo, per M3) agent there. Combined with M1 — where an injected agent picks the `cwd` via `remuda_instance_create` — the "unit of work" is not bound to any workspace at all.
- **Fix:** Canonicalize `request.cwd` and reject it unless it resolves inside the registered workspace/worktree root.

### F8. `/yes` approves whichever ticket is newest, and grants session-wide rather than once

- **Where:** `crates/remuda-feishu/src/dispatcher.rs:851-868` `cmd_yes_no` resolves the target as `self.tickets.latest_open(key, now)` — the newest open ticket for the session, bound to **no** specific interaction id, tool name, or input digest. The action string is `"allow"` (`dispatcher.rs:683`), which `tickets.rs:304-311` `effect_for_a` maps to `DecisionEffect::AllowSession`, the broadest grant, rather than `AllowOnce` (which exists, as `"once"`).
- **Exploit:** Two failure modes, both realistic. (1) **Race:** the owner reads card A, types `/yes`; card B (a different, more dangerous tool call) arrives in between; `latest_open` returns B and the owner approves the wrong thing with no echo of what was approved. (2) **Content influence:** message text can be attacker-influenced even from an owner's account — forwarded blocks, quoted agent output, a group member's pasted text. An owner relaying a block that begins with `/yes` silently approves the pending call. The blast radius is then session-wide, not one call.
- **Fix:** Bind `/yes` to an explicit ticket reference, or accept it only when exactly one ticket is open and echo the tool being approved. Map `/yes` to `AllowOnce`; reserve `AllowSession` for a deliberate card click. Invalidate the shortcut if the newest ticket changed since the last card was posted.

### F9. Card answers cross-check nothing between the ticket and the session that answers it

- **Where:** `crates/remuda-feishu/src/tickets.rs:157-167` `answer_callback` looks up purely by `callback.tid` and never compares `ticket.session_key`. `dispatcher.rs:908-916` `commit_answer` then takes `binding.instance_id` from the *card action's* chat→session binding but `interaction_id` from the *ticket* — two independent sources, no cross-check. `/new` (`dispatcher.rs:753-777`) does not expire open tickets, so `latest_open` can return one belonging to a retired instance.
- **Exploit:** Mostly fails safe today — the Hub's `requestVersion`/`processGeneration` CAS rejects a stale interaction against the wrong instance — so this is a correctness/authz gap rather than a live break. It matters in multi-owner deployments, where any owner can answer any other owner's ticket, and it is one CAS change away from being exploitable.
- **Fix:** Require `ticket.session_key == inbound.session_key` in `answer_callback`, resolve the instance from the ticket's session, and expire tickets on `/new` and `/stop`.

### S1. Agent child processes inherit the Node's entire environment — `env_clear` appears nowhere in the tree

- **Where:** `crates/remuda-driver/src/claude_print.rs:270-277` builds the child with `Command::new(...)` and then only *adds* variables (`for (key, value) in &env { command.env(key, value); }`), same pattern at `claude_bg.rs:292-303`. `rg env_clear crates/` returns **nothing**. The recipe's `env_allowlist` is purely additive — it decides what to inject, it strips nothing.
- **Exploit:** Every secret in the Node's own environment is inherited by the spawned agent CLI and is therefore readable by the model and by any tool it runs — a Bash tool inside the agent need only run `env`. That includes `REMUDA_BOOTSTRAP_TOKEN` (which `carrier.rs:66-71` and `enroll.rs:50-53` read from env, and which A1/A2 make catastrophic), `REMUDA_HOST_TOKEN`, `ANTHROPIC_API_KEY`, and any operator gateway credential. This is a direct secret-isolation break on the *default* driver path, not a hypothetical.
- **Note on scope:** this is the print/bg path. The PTY paths pass an explicit curated map to herdr (`claude_pty.rs:239-243`, `generic_pty.rs:357-367`) — but per G4 the herdr *daemon* was itself spawned with the Node's env, so the pane inherits it anyway. Both paths leak; they just leak at different layers.
- **Fix:** `command.env_clear()` before injecting, then add only the allowlisted names plus the minimum a CLI needs (`HOME`, `PATH`, `TERM`, locale). Pair with G4's daemon-env scrub, or the PTY path stays leaky regardless.

### S2. `env` allowlisting has a two-name denylist, so loader and proxy variables would pass

- **Where:** `crates/remuda-driver/src/flags.rs:53` `BANNED_ENV: &["CLAUDE_CODE_SIMPLE", "CLAUDE_CODE_SAFE_MODE"]`, enforced by `reject_spec_env` (`materializer.rs:846-855`). Nothing rejects `LD_PRELOAD`, `LD_LIBRARY_PATH`, `NODE_OPTIONS`, `PATH`, `ANTHROPIC_BASE_URL`, `HTTPS_PROXY`, or `SSL_CERT_FILE`. `EnvBinding::HostEnv(name)` additionally lets a spec pull any named Node env var into the child (`claude_print.rs:387-391`).
- **Exploit:** Code execution (`LD_PRELOAD`, `NODE_OPTIONS`) or silent traffic redirection and TLS interception (`ANTHROPIC_BASE_URL`, `HTTPS_PROXY`, `SSL_CERT_FILE`) in the agent process.
- **Gating, stated plainly:** production `instance_spec` sets `env: BTreeMap::new()` (`native.rs:437`), so `spec.env` is empty today and this is **not currently reachable**. It is a P1 because the materializer is the boundary that is *supposed* to enforce this, and it does not — one caller that forwards request env turns it on.
- **Fix:** Replace the denylist with a strict allowlist of injectable names, and reject the loader/proxy/TLS/PATH family regardless of origin.

### V1. Device token and access code live in `localStorage`, and the token is put in the WS query string

- **Where:** `web/src/lib/session.ts:36-44` writes the device token to `localStorage`, and `web/src/lib/api.ts:619`/`:628` write the *same* token a second time via `writeAccessCode(body.token)` → `accessCode.ts:16`. `accessCode.ts:30` then sends it as `Authorization: Bearer`. `web/src/lib/api.ts:349-355` `followUrl` puts `readSession()?.token ?? readAccessCode()` into `?token=`, and the Hub accepts it there (`ws.rs:108-113`).
- **Exploit:** Two distinct problems. (1) The Hub deliberately issues the token as an **HttpOnly, SameSite=Strict** cookie (`auth.rs:112-119`) and the client already sends it via `credentials:"include"` (`api.ts:364`) — then stores a JS-readable copy in two `localStorage` keys, discarding exactly the protection the backend provides. Any XSS exfiltrates a 30-day token. (2) Tokens in a URL leak into reverse-proxy logs (the runbook's Caddy) and browser history. The Hub itself installs no HTTP request logging (no `tower_http` `TraceLayer`), so on pure loopback the token does not reach a Hub log — history and any fronting proxy still see it.
- **Note:** the app's own Settings hint says `不要把长期 token 放进 WebSocket URL` — "do not put the long-lived token in the WebSocket URL" (`web/src/pages/SettingsPage.tsx:66`). `followUrl` does precisely that. The intent is already documented in-tree; only the implementation disagrees.
- **Fix:** `/v1/follow` already falls back to cookie auth (`ws.rs:115`), and same-origin WS handshakes send cookies — so drop the `?token=` parameter outright rather than inventing a ticket scheme. Stop writing the token to `localStorage`; keep only non-secret `deviceId`/`name` for UI.

### V2. No CSP, no `X-Frame-Options`, no `X-Content-Type-Options` on any Hub response

- **Where:** `crates/remuda-hub/src/web.rs:45-52` `file_response` sets only `Content-Type`; `web/index.html:1-24` has no CSP `<meta>`. Grep for `Content-Security-Policy|X-Frame-Options|frame-ancestors|X-Content-Type` across `web/` and `crates/` returns nothing.
- **Exploit:** Clickjacking on a control plane whose whole job is approving tool calls — frame the Hub, overlay bait, harvest approval clicks against `POST /v1/interactions/{id}/answer`. `SameSite=Strict` does not help here: the framed document is same-origin and authenticates with the `localStorage` Bearer token from V1. No CSP also means any XSS gets unrestricted script execution and exfiltration, which is what turns V1's stored credential into full account takeover. `index.html:14-18` also pulls fonts from `fonts.googleapis.com`/`gstatic.com`, so the app already has third-party origins in its supply chain.
- **Fix:** Send `Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'; base-uri 'none'; connect-src 'self' ws: wss:` (self-host the fonts, or allow the two font origins explicitly), plus `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and `Referrer-Policy: no-referrer`, from `file_response` so both embedded and `web_root` paths get them.

## What looks correct

- Review-1's H1 host binding is real and thorough: `ensure_instance` (`store.rs:655-658`), `append_journal` (`ws.rs:401`), `tty.frame` (`ws.rs:435-443` — explicit `instance.host_id != *host_id` → `Forbidden`), and `mark_settled` (`ws.rs:463`) all bind to the authenticated host.
